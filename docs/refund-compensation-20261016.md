# BillingSession 退款补偿与验收

日期：2026-10-16。独立分支 `codex/refund-compensation-20261016`，基于冻结的 PR #3 提交 `dae9a04a2`；与 Auto 标记修复分支互不依赖，不向 PR #3 追加提交。Draft PR 暂以冻结架构分支为 base 展示独立差异，基础提交进入 main 后再调整 base。

## 边界与数据模型

范围为 `BillingSession.Refund` 的钱包、订阅原始预扣、追加预扣及 Key 额度。保留价格、模型/渠道准入、Key 绑定与额度计算规则，不改支付回调或真实支付接口。其他异步模型任务既有的任务账务流程没有迁入此机制。

复用 `SubscriptionPreConsumeRecord` 的 request_id 幂等及池→记录锁顺序，复用 `SystemTask` 调度、数据库租约、失败状态和既有通知通道。新增一张 `BillingRefund` 持久化凭据表：原订阅记录无法描述钱包和 Key，也无法区分成功结算与失败退款，硬塞进原表会改变其业务含义。没有新增消息队列、外部数据库、outbox 服务或第三方依赖。标准/快速 AutoMigrate 均注册新表，未修改原有业务列。

凭据保存关联请求、用户/Key/权益 ID、各退款数量、追加预扣及结算目标、状态、失败次数、重试时间、错误及人工核对依据。prepared 中的数量代表待核对的目标，reserved 才代表已确认预扣。**不保存 Key 明文、支付密钥或支付凭据。**

## 状态与可靠性

1. 在预扣前建立 `prepared` 凭据，预扣成功保存准确退款数量后转为 `reserved`。资金和 Key 的这些可退款扣款直接写 SQL，绕开进程内批量队列；批量更新开关不再使退款对应的原扣款只存在内存中。
2. Refund 先同步将 `reserved` 转为 `pending`，再设置会话终态、异步执行；意图写入失败保留 NeedsRefund 和原凭据，不能把它标成已完成。
3. worker 在事务内锁退款凭据，验证原订阅记录归属及数量，并一起退还钱包或订阅原始/追加预扣、Key，最后写 `cache_pending`。中间任一步失败全部回滚。并发进程/重复投递由凭据行锁和状态控制，失败的提交确认可通过重读数据库安全恢复。
4. 提交后做幂等缓存失效，再转 `succeeded`。缓存失效或最终状态写入失败只重试此阶段，不再次入账。失败次数/错误和下次时间持久化；一分钟调度每次最多处理 100 条，指数退避从 60 秒到最多一小时，持续重试，不在第三次永久放弃。

单次退款数据库操作最多 30 秒，排队及失败状态记录各最多 10 秒，避免失效数据库连接无限占有退款行锁。后台取消在操作之间检查，不把网络超时当作未提交的证明。
5. 正常结算在操作资金前保存目标并转 `settling → settled`；资金已结算但 Key 调整失败保存错误并转 `review`，避免后台误退已结算资金。结果不明的 settling 不接受重复结算，防止提交确认丢失后再次扣款/加余额；明确的额度不足拒绝会恢复原 reserved 状态，原预扣仍可退款。

退款的锁顺序为“退款凭据 → 订阅池 → 原预扣记录 → Key”；钱包路径为“退款凭据 → 钱包 → Key”。会话状态更新在余额事务之外，避免把凭据锁放在余额锁之后。原有预扣/退款的池→记录顺序保留。

**不能自动判断的情况：**进程在既有多步预扣/追加预扣/结算中断，或数据库完全不可用、退款决定尚未写入时，持久化的 prepared/reserved/settling 凭据可以暴露待核对项，但不足以证明每一步都提交了。六小时未推进会进入告警统计；不能按超时猜测资金结果并自动退款。prepared/settling/review 不允许直接 confirm_refund；必须独立核对并完成必要纠正，再 confirm_settled 关闭。这是一条人工恢复路径，不声称本 PR 已把整个扣费与结算改造成原子账本。

## 对账、告警与人工处理

既有系统任务增加 `billing_refund` 周期任务。结果保存本轮完成/失败、待处理总数和告警数量；未完成退款即使处在退避窗口也不会显示为已清零。失败任务记录先提交，再尝试通过 root 用户现有通知方式发送告警，沿用通知频率限制。外部邮件/webhook 是尽力投递，失败任务与凭据是持久化的异常入口；未配置外部通知也不会丢弃待处理状态。

Root 权限接口，继续经过现有鉴权与管理员写操作审计：

| 接口 | 用途 |
|---|---|
| `GET /api/billing-refund/?status=failed&limit=20&offset=0` | 分页查看凭据、退款数量、失败次数、错误与待处理状态；也可查询 prepared/reserved/settling/review/cache_pending |
| `POST /api/billing-refund/:id/review`，action=`retry` | 对已有 pending/failed/cache_pending 退款立即解除退避，仍由幂等 worker 执行 |
| 同接口，action=`confirm_refund` | root 已核对请求确实失败且完整预扣仍在时，将 reserved 凭据确认为退款意图；不接受结果不明的 prepared/settling/review |
| 同接口，action=`confirm_settled` | 独立对账及必要纠正已完成后关闭结果不明的凭据，不修改余额 |

人工操作必须提供 8–1000 字节的 reason，凭据原子记录 ReviewedBy/ReviewReason。普通用户和普通管理员均被拒绝。接口不接受任意入账金额，也不将旧 consumed 记录批量退款。没有人工核对证据时应保留记录等待处理。

## 清理保护与发布/回滚边界

- 非终态退款凭据不清理；成功退款和已结算凭据至少保存 30 天。
- 七天原预扣清理只删除已退款或已有持久化结算依据的记录，并排除未完成退款引用的记录。旧 consumed 无法判断终态，继续保留供核对。
- 已结算凭据在对应 consumed 记录尚未清理时也保留，避免清理顺序先删掉结算证据。
- 本 PR 只在隔离环境执行迁移，没有访问生产数据库。将来上线需先审核新表迁移及任务容量；回滚程序前先停止接收新请求并完成/导出非终态凭据，不能让旧版本忽略尚未完成的退款。该发布操作不属于本次授权执行。
- 多节点升级需同时替换会运行原预扣清理的旧节点；不能长期保留旧版无状态筛选的七天清理任务，与新补偿 worker 混跑。没有在本次任务中执行任何发布步骤。

## 测试证据

隔离 SQLite 临时库、loopback PostgreSQL 16.14 私有集群和合成数据；Redis 使用 miniredis。没有真实支付、生产账户、生产快照或付费上游调用。

- 并发重复退款只入账一次；池、追加预扣、Key 及完成标记任一步失败一起回滚。
- 丢弃会话内存后，worker 仅凭 SQL 中退款意图完成恢复；启用批量更新时原扣款也已落 SQL。
- 连续失败三次仍保留可重试凭据、次数和错误，恢复后由任务完成，不需要重建会话。
- Redis 故障发生在退款 SQL 提交之后：数据库额度已恢复，状态 cache_pending；重试只完成缓存阶段，不重复入账。
- **真实 PostgreSQL 提交确认丢失：**仅连接隔离测试库的协议代理等到服务器已返回 COMMIT，再断开客户端连接，实际提交成功、客户端得到错误；重试后仍只入账一次。
- 意图写入失败保留 reserved 凭据与 NeedsRefund；到期进入对账告警，root 核对后安全排队恢复。
- 额度不足导致追加预扣/结算拒绝后，原预扣仍能退款；字段上溢、错归属、异常终态不能入账。
- 清理顺序与保留期测试保护 pending、failed、cache_pending 和结果不明/历史凭据。
- Root HTTP 权限、审阅依据持久化及响应无凭据泄露；现有系统任务会创建并保存失败对账记录。

最终完整后端、PostgreSQL race、静态检查结果及仍未验证项目在 Draft PR 的 Proof of Work 补录。前端三项 Auto 既有失败由独立 PR #4 处理，本退款分支不混入该 UI 改动。MySQL 实例和真实进程崩溃/机器断电未运行，不能把协议断连和丢弃会话内存的测试夸大为完整灾难恢复演练。
