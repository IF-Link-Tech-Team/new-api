# 最简生产发布与回退清单

适用：人工审阅 [集成验收报告](integration-acceptance-20261016.md)后执行。**本文件是待执行清单，不是已上线记录或授权；本轮没有执行以下生产操作。** A 为 #6（仅 #3 + #4），B 为将来单独验收的 #5；不能把 B 当作已包含在 A 中。

## 发布前

- [ ] 维护者确认准确 commit、镜像 digest、回退镜像、责任人和观察窗口；确认本次发布是否仅 A。#6 的人工合并不会自动批准发布。#3/#4 不再重复合入；#5 后续须单独集成并重跑完整 CI。
- [ ] 备份完整主数据库；日志库若独立则一起备份，保存 Schema、数据库版本、配置与密钥恢复位置、订单/权益/Key/余额/原预扣及任务记录，采用受控加密保管。记录备份时间点与交易边界，在隔离环境实际恢复并检查关键记录；未验证恢复的备份不算完成。
- [ ] 从恢复副本预演目标版本的启动迁移与业务不变量；核对价格、额度换算、套餐/流量包、模型/渠道/fallback 和 Key 绑定没有配置漂移。不得对真实订单重放支付回调做测试。
- [ ] 明确退款风险处置：A 沿用旧异步退款机制，必须落实失败日志告警、值守与独立对账、幂等记录保留；不能对所有 consumed 自动退款。若无法保证证据保留和人工处理，应推迟发布，等待 #5 完成独立发布门槛。
- [ ] 若发布 B：容量、积压恢复目标、告警送达/失联监控、迁移与回退演练全部完成；清点 prepared/reserved/settling/pending/failed/cache_pending/review 记录、最老时间、关联原预扣和任务状态。缺少核对证据不能清零或强行改终态。

## 切换与观察

- [ ] 按已批准维护窗口控制流量和资金相关新写入，等待在途请求、异步退款与既有进程内批量更新结束并核对 SQL 余额；保存切换交易边界。保持支付回调重试/补单的幂等约束，不能靠重复人工入账“验证”。
- [ ] B 必须在接流量前完成新表迁移，并停止所有会执行旧预扣清理的 master 进程；旧维护任务启动时也可能清理。当前没有独立清理开关，不能假设滚动混跑安全。不要删除新表或历史 consumed 记录。
- [ ] 观察认证错误、模型调用成功率与延迟、渠道 fallback、Fresh/Cached/Output 计费与余额、支付订单/权益发放、Key 额度和绑定；通过已授权的只读对账检查，避免真实交易测试。
- [ ] B 额外观察退款各状态数量、最老未完成时间、重试次数、cache_pending、review、最近成功任务/心跳、实际排空速度，以及 SQL 连接、锁等待/死锁、写入/WAL、磁盘和表增长。通知必须实际可达；不能仅凭“任务保存失败”或“发送函数返回 nil”判断已告警。预先约定阈值与值守人，超出恢复目标或任务停摆立即处置。

## 异常与回退

- [ ] 出现重复入账、额度不符、异常权益或持续退款失败，先限制受影响的新写入，保留请求 ID、订单、池、Key、凭据及任务证据。暂停会销毁证据的进程；不要批量重放回调、补单或退款。
- [ ] A：确认在途请求、退款和批量队列已处理/记录，再回退到已保存的程序镜像。正确完成的新充值/结算继续有效，不能用上线前整库恢复覆盖它们；异常逐单独立对账。
- [ ] B：回退旧程序前先保护全部非终态凭据与其原预扣证据。仅在完整核对、处理并确认无遗留责任后回到旧任务体系；否则保留可运行的 #5 兼容补偿节点/Schema、停止新流量并人工处置。旧 master 清理仍未停止时不得继续回退。若无法安全保留补偿与证据，暂停回退，不能把“旧进程能启动”当作成功。
- [ ] prepared/settling/review 等结果不明项先独立核对数据库/调用结果，必要时受控纠正并记录依据。`retry` 仅用于已有退款意图；`confirm_refund` 只接受已核对且完整预扣仍在的 reserved；`confirm_settled` 不修改余额。保留审核人和原因。
- [ ] 不 DROP BillingRefund、不清空任务/非终态数据、不为了压低积压而删除记录。确需灾难恢复时，由维护者批准恢复点、增量交易重放与对账方案；恢复后重新核对订单、权益、用户余额和 Key，再决定恢复流量。

发布负责人、备份恢复证据、容量/告警证据和人工批准未齐备时，保持 Draft/待发布状态。
